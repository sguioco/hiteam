# Локальная среда приёмки UX

Для проверки ролей и локаций есть отдельный tenant `qa-ux-acceptance` в локальной Docker-базе. Он не связан с продом и не перезаписывает `demo`.

## Создание фикстуры

После запуска локальных PostgreSQL и API выполните из `apps/api`:

```bash
DATABASE_URL='postgresql://smart:smart@localhost:5433/smart' \
QA_ACCEPTANCE_PASSWORD='<локальный тестовый пароль длиной от 12 символов>' \
node scripts/seed-ux-acceptance.cjs
```

Скрипт принимает только loopback-адрес БД и отказывается перезаписывать уже созданный tenant. Не запускайте обычный `prisma/seed.ts` для этой задачи: он пересоздаёт часть данных tenant `demo`.

## Учётные записи

Откройте `http://localhost:3000/login` и войдите с паролем, заданным при создании фикстуры:

| Роль | Email |
| --- | --- |
| Владелец | `qa-owner@ux-acceptance.invalid` |
| Менеджер | `qa-manager@ux-acceptance.invalid` |
| Сотрудник | `qa-employee@ux-acceptance.invalid` |

Если форма просит выбрать workspace, используйте `qa-ux-acceptance`. Для смены роли выходите из текущего аккаунта и входите под другим. Не используйте `owner@demo.smart`: для него веб-клиент может включить демонстрационный режим с подменёнными данными.

Фикстура содержит одну компанию, три локации (`Head office`, `North warehouse`, `South retail`) и по одной задаче в каждой. Владелец и менеджер получают реальные ответы API по локациям; сотруднику `/org/locations` недоступен по текущим правам. Это исходные данные для ролевой и мульти-локационной приёмки, а не имитация полного производственного наполнения.

Проверено локально 24 сентября 2026: вход через API и веб-форму успешен для всех трёх ролей; `/org/locations` возвращает три локации владельцу и менеджеру, сотруднику — 403. Под сотрудником действие «Start» перевело назначенную QA-задачу в `In progress`. Подробнее — в плане UX-аудита.
