## Подтверждённые дефекты

### F-01 · P1 · Обход запрета доступа к рабочему пространству

- **Воспроизведение:** авторизовать employee; установить его `workspaceAccessAllowed=false`; вызвать `GET /collaboration/tasks/me` с ранее выданным JWT.
- **Факт:** HTTP 200 и задача сотрудника. Ожидается 403.
- **Причина:** глобальный `WorkspaceAccessGuard` выполняется до controller-level `JwtAuthGuard`. При отсутствии `request.user` он разрешает запрос, последующей проверки workspace нет.
- **Где:** `src/common/guards/workspace-access.guard.ts`, `src/app.module.ts`, `src/modules/auth/guards/jwt-auth.guard.ts` в apps/api.
- **Риск:** серверный запрет pending-access не работает. Проверка оплаты в этом же guard также оказывается вне авторизованного контекста; платёжные сценарии требуют отдельного подтверждения.
- **Исправление:** единый порядок authentication → workspace/billing authorization → роли/scope. Проверить ранее выданные токены и исключения AllowPendingAccess интеграционными HTTP-тестами.

### F-02 · P1 · Чужой закрытый групповой чат доступен через POST

- **Воспроизведение:** owner создаёт группу только с собой и групповой чат. Employee, не входящий в группу, вызывает GET чата и POST `/collaboration/chats` с тем же `groupId`.
- **Факт:** GET возвращает 403, POST возвращает 201 и объект существующего чата.
- **Причина:** `createChat` проверяет tenant группы, но не membership/участие. Existing thread возвращается напрямую с `chatInclude`; при создании нового чата requester добавляется в участники автоматически.
- **Где:** `apps/api/src/modules/collaboration/collaboration.service.ts:3875`.
- **Исправление:** одинаковая проверка участия для всех путей чтения/создания группового чата, без возможности самостоятельного вступления через chat API. Воспроизведение сделано на пустом чате; выдача сообщений следует из общего include в исходниках.

### F-03 · P1 · Фотоотчёты доступны анонимно и кэшируются на год

- **Воспроизведение:** employee загружает синтетическое PNG в photo-required task; открыть `/media/task-photo-proofs/<id>/file` без Authorization.
- **Факт:** HTTP 200, `Cache-Control: public, max-age=31536000, immutable`.
- **Причина:** StorageController не имеет auth guard; запрос ищет proof по UUID без tenant, разрешений на задачу и проверки удаления самой задачи.
- **Где:** `apps/api/src/modules/storage/storage.controller.ts:22`.
- **Риск:** знание/утечка ссылки даёт постоянный доступ к рабочему фото. UUID — не механизм авторизации; публичное кэширование осложняет отзыв доступа.
- **Исправление:** авторизованная доставка либо короткоживущие подписанные ссылки после проверки разрешений. Проверять lifecycle задачи/proof и использовать соответствующую политику кэша. Учесть Image/link клиентов при изменении контракта.

### F-04 · P1 · Scope менеджера не применяется к балансам и payroll

- **Воспроизведение:** дать manager scope `location` South retail. GET `/org/locations`, `/requests/balances`, `/payroll/summary`.
- **Факт:** org отдаёт одну разрешённую локацию; balances отдаёт всех трёх сотрудников, включая owner из Head office; payroll считает всех трёх.
- **Причина:** контроллеры requests/payroll передают tenantId без разрешённых employee/location IDs. ListBalances/summary фильтруют по tenant, а не scope.
- **Где:** `apps/api/src/modules/requests/requests.controller.ts`, `requests.service.ts:289`; `apps/api/src/modules/payroll/payroll.controller.ts`, `payroll.service.ts:17`.
- **Риск:** раскрытие кадровых/зарплатных данных других филиалов. Endpoint изменения балансов также требует scope-проверки; изменение чужого баланса в этом тесте не выполнялось.
- **Исправление:** общий серверный resolver доступных сотрудников, применяемый к чтению, экспорту и изменению данных. Проверить location/company/tenant scope отдельно.

### F-05 · P1 · Смена создаётся в часовом поясе сервера вместо локации

- **Воспроизведение:** локация Europe/Moscow, шаблон 09:00–18:00, смена 2026-10-07.
- **Факт:** API сохраняет `09:00Z–18:00Z`; ожидается `06:00Z–15:00Z`. Браузерный календарь показывает 12:00–21:00.
- **Причина:** `mergeDateAndTime` использует `Date.setHours`; timezone локации не участвует в преобразовании даты и локального времени в UTC.
- **Где:** `apps/api/src/modules/schedule/schedule.service.ts:883`, вызовы при создании/редактировании и fixed break.
- **Риск:** неверное расписание, опоздания, расчёт времени и публикация смен в Altegio. UAE и DST-зоны тоже требуют регрессии.
- **Исправление:** единый контракт local date + HH:mm + location IANA timezone → UTC; тесты ночных смен, переходов DST и двух локаций с разными поясами.

### F-06 · P2 · Можно создать одинаковые и пересекающиеся смены

- **Воспроизведение:** дважды POST `/schedule/shifts` с одинаковыми employeeId/templateId/shiftDate.
- **Факт:** оба запроса 201, в календаре несколько одинаковых смен.
- **Причина:** нет проверки пересечения временных интервалов или идемпотентности; индекс employee/date не уникальный.
- **Где:** `apps/api/src/modules/schedule/schedule.service.ts:386`, модель Shift.
- **Исправление:** продуктово определить допустимые несколько смен в день; запретить пересечение опубликованных интервалов и повторы, включая конкурентные запросы, bulk assignment и импорт. Не вводить запрет всех нескольких смен без этого решения.

### F-07 · P1 · Будущие смены вытесняют ближайшие из календарной выдачи

- **Воспроизведение:** добавить 51 смену сотруднику на январь–февраль 2027 при существующей смене 7 октября 2026. Вызвать `/schedule/me` и `/schedule/shifts`.
- **Факт:** 200, соответственно 30 и 50 смен; ни одной октябрьской смены.
- **Причина:** сортировка shiftDate DESC + take 30/50 без диапазона дат. `bootstrap.schedule` вызывает эти методы, в том числе при заданном visible range.
- **Где:** `apps/api/src/modules/schedule/schedule.service.ts:297`, `:737`; `apps/api/src/modules/bootstrap/bootstrap.service.ts:1555`.
- **Исправление:** серверный диапазон отображаемого календаря и явная пагинация; employee/admin должны получать все разрешённые смены диапазона. Не просто повышать лимит.

### F-08 · P2 · Невалидное время принимается в шаблон смены

- **Воспроизведение:** создать template с startsAtLocal=`nonsense`, endsAtLocal=`18:00`.
- **Факт:** шаблон сохраняется (201), попытка создать по нему смену возвращает 400.
- **Причина:** DTO проверяет IsString, а проверка HH:mm не является инвариантом шаблона. Пользователь получает рабоче выглядящий, но непригодный шаблон.
- **Где:** `apps/api/src/modules/schedule/dto/create-shift-template.dto.ts`, `schedule.service.ts:310`.
- **Исправление:** нормализованный тип локального времени/валидация диапазона при создании шаблона, фиксированных перерывов и обновлениях. Нужна проверка уже сохранённых шаблонов.

## Дополнительные риски — не выдавать за воспроизведённые инциденты

1. **Удаление аккаунта и биометрия.** `auth.service.ts:1005` удаляет DB-профили и обнуляет avatarStorageKey, но не вызывает удаление storage-объектов и Face IDs у провайдера. Нужно проследить retention worker и весь lifecycle, проверить удаление на тестовом S3/Rekognition окружении. Production-удаление не выполнялось.
2. **Конкурентность отпусков.** `requests.service.ts:837` читает status до transaction, обновляет step по id без status-CAS; `:1287` резервирует баланс через read → абсолютный pendingDays. Архитектурно возможны гонки. В одном реальном конкурентном approve-прогоне получено 201/400, баланс корректен (2 used, 0 pending); двойное списание этим прогоном НЕ подтверждено. Нужен детерминированный concurrency-тест.
3. **Неполное подключение тестов.** `attendance-correction-access.test.ts` и `activity-task-links.test.ts` отсутствуют в списке run-api-tests.ts. Проверить, как они включаются в CI, прежде чем считать защищёнными регрессии соответствующих сценариев.
4. **Доступность веба.** В accessibility tree есть безымянная кнопка раскрытия меню сотрудников и безымянное поле поиска списка сотрудников. Нужны accessible names и полноценный клавиатурный прогон. Это локальное UI-наблюдение, а не завершённый WCAG-аудит.
