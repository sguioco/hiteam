## Цель

Владелец должен самостоятельно настроить компанию, пригласить сотрудника, назначить смену и задачу, увидеть результат и разобраться в отклонениях. Сотрудник должен принять приглашение, завершить регистрацию, отметить приход/уход и сдать задачу с фотографией без технических тупиков.

Приоритеты:

- **P0:** невозможно завершить ключевой сценарий.
- **P1:** сценарий затруднён, действие недоступно или его результат непонятен.
- **P2:** навигация, согласованность интерфейса и скорость ежедневной работы.
- **P3:** дополнительные улучшения и развитие механик.

Критерий завершения: у каждого пункта есть подтверждённый статус и воспроизводимый сценарий либо объяснение, почему он не воспроизводится. P0 разбираются сразу после воспроизведения, без ожидания полного аудита остальных экранов.

## Этап 3. Настройка компании и первое использование

- [ ] **ONB-01 / P1:** организовать короткий пошаговый сценарий настройки с прогрессом и возвратом без потери введённых данных.
- [ ] **ONB-02 / P1:** явно предложить режим работы: учёт посещаемости с задачами либо только задачи и чек-листы. Запрашивать лишь нужные выбранному режиму настройки; сохранять необходимые организационные данные.
- [ ] **ONB-03 / P1:** объяснить, какие разделы доступны до завершения настройки и что нужно сделать для остальных. Не оставлять меню визуально активным без объяснения блокировки.
- [ ] **ONB-04 / P2:** добавить объяснение геозоны: что означает радиус и как он влияет на отметку прихода. Отделить радиус от точности определения местоположения.
- [ ] **ONB-05 / P2:** добавить возврат на публичную главную из авторизации.
- [ ] **ONB-06 / P1:** после настройки предложить следующий шаг: пригласить сотрудника и создать смену/задачу в зависимости от режима.

Критерии приёмки:

- Новый владелец проходит настройку без устных подсказок.
- Режим «только задачи» не требует неиспользуемой настройки биометрии и геозоны.
- Смена шага и ошибки не сбрасывают форму; успешное завершение видно пользователю.
- Ориентир 2–3 минуты из аудита проверяется пользовательским прогоном, а не объявляется достигнутым заранее.

Источник: Аудит 1, первый контакт нового владельца.

## Этап 4. Задачи и активность как рабочие разделы

- [ ] **TASK-01 / P1:** основное представление — список задач с исполнителем, сроком, локацией и явным статусом. Сохранить группировку по сотрудникам как дополнительный режим.
- [ ] **TASK-02 / P1:** открывать карточку задачи из списка, главной и активности. Использовать общий компонент просмотра и доступных действий.
- [ ] **TASK-03 / P1:** обеспечить предусмотренные продуктом действия: редактирование, удаление, завершение, комментарии и просмотр фото. Сначала проверить API и права; недостающие возможности оформить отдельными подзадачами.
- [ ] **TASK-04 / P2:** выделить поиск, согласовать фильтры с календарём, показать текстовые статусы «ожидает», «выполнено», «просрочено» согласно фактической модели данных.
- [ ] **ACT-01 / P1:** переходы из события к задаче и профилю сотрудника с сохранением контекста списка; обработка удалённых и недоступных объектов.
- [ ] **ACT-02 / P2:** объяснить роли аватаров — автор действия и исполнитель — либо убрать визуальный дубль, если отдельного смысла нет.
- [ ] **ACT-03 / P2:** добавить фильтры типов событий, если подтверждена потребность и данные их поддерживают.

Критерий приёмки: менеджер находит задачу, открывает её, выполняет разрешённое действие и видит обновлённое состояние без поиска по карточкам каждого сотрудника. Ошибка сохранения видна, введённые данные остаются. Роль сотрудника не получает действия менеджера.

Источник: Аудит 2, задачи и активность; Аудит 1, лента главной.

## Этап 5. Главная и календарь

- [ ] **HOME-01 / P2:** повысить приоритет посещаемости для полного режима: кто на месте, опаздывает и не пришёл; предусмотреть переход к деталям. Для режима «только задачи» главным остаётся выполнение задач.

- [ ] **HOME-04 / P2:** сделать просроченные задачи заметными: понятная иконка, счётчик и переход к отфильтрованному списку.
- [ ] **HOME-05 / P2:** уменьшить визуальный вес недельного календаря, убрать повтор месяца в каждой ячейке, выделить сегодня, добавить прошлые/следующие периоды и переход в полный календарь.

- [ ] **EMP-02 / P2:** убрать дубли назначения команды/бригады, объединить второстепенные действия в меню; устранить лишний горизонтальный скролл.
- [ ] **INV-02 / P2:** вынести приглашения в компактную вкладку или секцию со счётчиком, поиском и пагинацией; сохранить повторную отправку и доступные действия.
- [ ] **MOB-03 / P1:** добавить предпросмотр и пересъёмку фотографии до подтверждения биометрии. Изменение уже зарегистрированной биометрии проверить отдельно с учётом текущих правил доступа.
- [ ] **MOB-04 / P1:** проверить доступность сотруднику истории приходов/уходов и причины её отсутствия у аудитора. Сделать вход в историю очевидным в режиме учёта посещаемости.
- [ ] **MOB-05 / P2:** проверить существующий сценарий запроса корректировки времени; показать причину, статус рассмотрения и результат. Если функции нет, оценить отдельную разработку с журналом действий.
- [ ] **MOB-06 / P2:** показывать понятные причины неуспешной отметки: геозона, разрешения, распознавание, сеть — с уместным следующим действием.
- [ ] **MOB-07 / P3:** добавить или улучшить ручной ввод времени наряду с текущим picker; валидировать часы/минуты и учитывать локальный формат времени.

Критерий приёмки: список сотрудников и 50+ приглашений остаётся управляемым; разрешённые действия понятны. Сотрудник видит свою историю в соответствующем режиме и понимает, как сообщить о расхождении; запрос корректировки не меняет учётное время без предусмотренного решения.

Источники: Аудит 2, сотрудники; Аудит 3; Аудит 1, потребности сотрудника и владельца.

## Предложения, которые не включаются автоматически

| Предложение из аудита | Решение в плане |
|---|---|
| Радиус 30–50 м для кафе, 100–150 м для склада | Проверить точность позиционирования и действующие ограничения. Не менять пороги по одному примеру из макета. |
| Предупреждение, что в геозону попадают другие объекты | Отдельно оценить пользу и источник геоданных; не требуется для понятного объяснения геозоны. |
| Денежные премии и выходные за очки | Отдельная продуктовая задача: правила, настройки работодателя и связь с расчётами. Пока объяснить существующий рейтинг. |
| Полностью перенести мобильный дизайн в web | Использовать общие визуальные принципы, сохранив подходящую для desktop плотность и таблицы. |
| Скрыть всё меню до завершения настройки | Применять блокировку только там, где настройки действительно необходимы, с объяснением причины. |

## Порядок выпуска и зависимости

1. **Проверка и срочный выпуск:** этап 0, подтверждённые MOB-01/MOB-02, WEB-01, FORM-01 и INV-01. Мобильный выпуск отдельно от web/API.
2. **Общие компоненты и первый вход:** этапы 2–3; проверить, что переиспользование компонентов не меняет поведение остальных страниц.
3. **Ежедневная работа:** этапы 4–5; карточка задачи и общий контекст фильтров нужны до подключения переходов из главной и активности.
4. **Сотрудники и мобильные улучшения:** этап 6; историю и корректировки строить поверх проверенной модели прав и существующих API.
5. **Рейтинг и полировка:** этап 7 после основных сценариев.

Сроки и исполнителей назначить после этапа 0. Не оценивать технические сбои и новые функции как одинаковые по объёму UI-правки.

## Проверки перед выпуском

- [ ] Роли: владелец, менеджер и сотрудник; переходы и действия соответствуют правам.
- [ ] Режимы: полный и «только задачи»; одна и несколько локаций; пустые и заполненные списки, длинные названия, 50+ приглашений.
- [ ] Web: основные размеры ноутбуков и узкий экран, клавиатурная навигация, масштабирование, отсутствие перекрывающих кнопки заголовков.
- [ ] Языки: русский и английский; для других поддерживаемых языков проверить длинные строки, для арабского — RTL, если он включён в текущей сборке.
- [ ] Mobile: камера/галерея, отказ в разрешении, отмена выбора, повторная попытка, нестабильная сеть, возврат из фона.
- [ ] Сквозной сценарий: компания → приглашение → регистрация → смена/задача → отметка/фотоотчёт → результат у руководителя.
- [ ] Тесты на подтверждённые дефекты, проверки типов и сборка затронутых приложений; не заменять проверку поведения тестами на текст исходников.
- [ ] После изменения кода Docker Compose пересобрать и перезапустить затронутый сервис, проверить его через `docker compose ps <service>`.
- [ ] После публикации сверить версию сборки и проверить исправленный сценарий; для Android зафиксировать номер распространяемой сборки.

Пункты остаются открытыми до проверки свежего APK: выбор камеры/галереи, отмена, отказ в доступе, завершение регистрации, отправка фотоотчёта и отсутствие дубля после повтора.

### Продолжение: восстановление черновика первого входа (ONB-01)

- Логотип и данные провайдера карты не сохраняются: пользователь предупреждён о повторном выборе логотипа и подтверждении точки. Недоступность browser storage показывается явно, форма остаётся работоспособной.
- Регрессионные проверки покрывают сериализацию, срок, некорректные типы и разделение ключей. Браузерная приёмка перезагрузки, смены workspace и полного пути остаётся открытой.

### Продолжение: режим «только задачи» без геозоны (ONB-02)

- Форма вместо карты требует страну для биллинга. Адрес, координаты и радиус не требуются; часовой пояс и организационные данные сохраняются. На сервере отсутствующие координаты представлены NULL, миграция только снимает NOT NULL и не удаляет существующие значения.
- Настройка режима задач остаётся завершённой после повторного чтения API. Страна в ISO-формате определяет тариф независимо от карты и имеет приоритет над часовым поясом.
- Включение посещаемости требует настроенной карты для всех активных локаций; регистрация посещения без координат запрещена. Существующие координаты при выборе режима задач сохраняются.
- Добавлены проверки DTO, сохранения/повторного чтения, страны тарифа, границ workspace и обратного переключения. Браузерная и мобильная приёмка остаются открытыми.

### Продолжение: первый вход по шагам (ONB-01 / ONB-02 частично, ONB-04)

- Для первой настройки добавлены два шага: компания и явный выбор режима, затем рабочая локация. Переход вперёд проверяет название; назад не сбрасывает черновик и не сохраняет частичную компанию на сервере. Настроенные компании остаются в прежнем режиме редактирования.
- При смене шага фокус переходит на заголовок. Финальное сохранение использует прежний API и существующий переход к приглашению сотрудников.
- Шаги определяются незавершённой настройкой, включая созданную при регистрации пустую локацию. Подтверждение точки до завершения настройки обновляет черновик без промежуточного сохранения на сервер.
- Добавлено объяснение геозоны и отличие радиуса от точности GPS.
- Пакет не закрывает ONB-02 целиком: обязательные адрес/координаты в режиме «только задачи» пока сохранены до согласования backend-контракта. Восстановление черновика после перезагрузки и сквозная приёмка остаются открытыми.

### Продолжение: ошибки настройки локации (FORM-01)

- Единая валидация возвращает поле и сообщение: название организации/локации, адрес или подтверждение точки. Форма показывает ошибку рядом с соответствующим элементом, переводит фокус и прокручивает его в видимую область без сброса введённых данных.
- Добавлена проверка числовых координат и диапазонов; нулевые координаты допустимы. Серверные ошибки остаются отдельным общим сообщением.
- Проверки валидатора покрывают пустые имена, адрес, неподтверждённую точку и некорректные координаты. Браузерная приёмка фокуса и прокрутки ещё требуется.

### Продолжение: контекст активности и сотрудники (ACT-01, частично)

- Период, компания и локация сохраняются в URL активности и восстанавливаются при возврате. Некорректный диапазон не используется; запоздавший ответ предыдущего запроса не подменяет актуальную ленту.
- В событиях добавлены ссылки на профили целевых сотрудников по точным employee ID. Автор события пока не превращается в ссылку: контракт допускает user ID вместо employee ID.
- Добавлены проверки восстановления диапазона и фильтров, некорректных дат и обратного диапазона. Сквозная ролевая приёмка и сохранение свёрнутых дней/позиции прокрутки остаются открытыми.

### Продолжение: переходы из активности к задачам (ACT-01 / TASK-02)

- Новые события создания задач записывают точные `taskIds`, включая пакетное создание. Лента главной и раздел активности показывают отдельные ссылки на связанные задачи. Старые события без ID не сопоставляются по названию.
- Ссылка открывает общую карточку в разделе задач. Точечный запрос использует существующие ограничения tenant/роли/области доступа списка менеджера; отсутствие результата объясняется как удаление или недоступность задачи.
- Возврат к ленте доступен обычной навигацией браузера. Сохранение всех фильтров ленты между переходами и ссылки на профили сотрудников остаются отдельными незавершёнными частями ACT-01.
- Проверка преобразования событий покрывает пакетные и старые события, а также некорректные ID. Локальная полная проверка API выявила ошибки в незавершённых изменениях Altegio и отсутствующие локальные типы; сквозная приёмка ещё не выполнена.

### Продолжение: карточка задачи с главной (TASK-02, частично)

- Строка задачи в виджете главной теперь открывает общую карточку. Смена статуса перенесена в явные действия внутри карточки; доступны перенос, комментарии и чек-лист по существующим правам API.
- Данные карточки берутся из актуального списка главной, результат операции обновляет этот список. Демонстрационные задачи сохраняют свой локальный сценарий смены статуса.
- Переходы из ленты активности остаются открытыми: требуется надёжный ID связанной задачи в контракте события. Браузерная и ролевая приёмка ещё не выполнены.

### Продолжение: основное представление задач (TASK-01, TASK-04)

- По умолчанию раздел открывает список задач: название, исполнитель или команда, локация, срок, текстовый статус и просрочка. Командные и неназначенные задачи не теряются из-за отсутствия строки сотрудника.
- Сохранён отдельный режим «По сотрудникам». Период, локация и поисковая строка общие; фильтры посещаемости и количества задач относятся только к режиму сотрудников.
- В списке задач добавлены поиск по названию/исполнителю/локации, фильтр статуса и просрочки, сброс поиска и статуса. Различаются пустой период и отсутствие совпадений.
- Оба режима открывают общую карточку. Проверки рендеринга покрывают командные/неназначенные задачи, поиск и фильтрацию локации. Визуальная приёмка ещё нужна; весь UX-план остаётся в работе.

### Продолжение: чек-лист и результаты поиска

- В карточке задачи пункты чек-листа переключаются через существующий API с теми же правами автора/исполнителя/команды. Для виртуальных задач переключение недоступно по текущему контракту API.
- Значение меняется после ответа сервера; повторный клик во время запроса заблокирован. Ошибка остаётся видимой, состояние пункта не подменяется успешным.
