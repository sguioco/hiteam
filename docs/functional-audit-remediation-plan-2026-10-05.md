# План правок HiTeam по функциональному аудиту

Дата: 5 октября 2026. Основание: [функциональный аудит](functional-audit-2026-10-05.md).
Статус: в реализации. Этот документ не заменяет предыдущий UX-план.

### Выполнено в первом подэтапе

- ACCESS-01: workspace/billing проверяется после JWT authentication. HTTP и WebSocket используют общий авторизатор; управление аккаунтом остаётся доступным при истечении оплаты.
- ACCESS-02: membership проверяется до создания/возврата закрытого чата; list/get/send/read учитывают актуальную группу. Участники chat синхронизируются с group в одной транзакции, включая получателей уведомлений. Доставка сообщений повторно проверяет membership и доступ пользователя, не полагаясь на старые socket rooms. Из chat DTO исключены passwordHash и прочие чувствительные поля User.
- ACCESS-04: общий EmployeeScopeService применяется к balances, bulk accrual, payroll и прямому/фоновому payroll export. Scoped-пользователь не получает jobs других пользователей через exports API.
- Подключены ранее пропущенные attendance-correction-access и activity-task-links и новый access-regression suite. Добавлен локальный HTTP-прогон `apps/api/scripts/test-access-http.cjs`.

ACCESS-03 **в реализации**: media endpoint переведён на JWT + task scope, web — на session-cookie proxy, mobile — на Authorization. Локальная storage allowlist исключает task-файлы. Полная приёмка и production storage/CDN rollout остаются открытыми; порядок выпуска — в `docs/task-photo-storage-rollout.md`. Другие пункты плана сохраняются.

## Порядок реализации

Работаем крупными, но независимо проверяемыми блоками: подготовка → доступ → расписание → дополнительные риски → сквозная приёмка → выпуск.
Для каждого блока: воспроизведение на актуальной сборке, исправление причины, регрессионные тесты, обновление статуса в этом файле. Подтверждённые дефекты F-01–08 отделены от рисков, требующих исследования.

## Блок 2. Целостность расписания

Последовательность внутри блока: TIME-01 + TIME-02 → CAL-01 → SHIFT-01 → DATA-01.

### TIME-01 · F-05 · Часовой пояс локации

- [ ] Единый преобразователь local date + HH:mm + IANA timezone → UTC для create/update, ночных смен и fixed breaks.
- [ ] Определить семантику shiftDate как локальной календарной даты, не зависящей от timezone сервера.
- [ ] Согласовать отображение времени в web/mobile и обмен с Altegio; явно обозначать пояс при работе с несколькими локациями.
- [ ] Проверить attendance matching, lateness и payroll, которые используют эти timestamps.

Приёмка: Moscow 09:00 → 06:00Z; Dubai 09:00 → 05:00Z; одинаковый результат при разных TZ сервера. Ночные смены, DST gaps/ambiguous times и перерывы имеют определённое, протестированное поведение.

### TIME-02 · F-08 · Валидные шаблоны

- [ ] Проверять HH:mm и допустимые значения в DTO/domain на create/update и fixed breaks.
- [ ] Явно определить правила равного начала/конца, перехода через полночь и размещения перерыва внутри смены.
- [ ] Показывать понятные ошибки у соответствующего поля в web/mobile.

Приёмка: `nonsense`, 25:00 и некорректные минуты отвергаются до сохранения; валидные дневные/ночные шаблоны работают; импорт использует тот же контракт.

### CAL-01 · F-07 · Полная выдача смен диапазона

- [ ] Передавать visible date range из bootstrap к schedule queries; фильтровать его на сервере с учётом контрактов даты/пояса.
- [ ] Убрать молчаливое усечение take 30/50 для календаря; при больших диапазонах использовать явную пагинацию с полным получением нужного окна клиентом.
- [ ] Проверить main widgets, employee calendar, manager calendar и смену месяца/локации.

Приёмка: ближайшие смены не исчезают при 51+ будущей смене; все разрешённые смены выбранного периода видны, включая границы месяца; чужие локации не попадают в выдачу.

### SHIFT-01 · F-06 · Дубли и пересечения

- [ ] Рабочее предложение: несколько непересекающихся смен в день разрешены; точные дубли и пересечения опубликованных интервалов запрещены. Подтвердить правило перед реализацией.

Приёмка: конкурентное создание одинаковых смен не создаёт две записи; пересечение ночных смен через границу суток обнаруживается; допустимые соседние смены и повтор webhook не ломаются.

## Воспроизведение локальных HTTP-регрессий

В `apps/api` установить `DATABASE_URL` на локальную БД и `QA_ACCEPTANCE_PASSWORD` на пароль синтетического fixture. Скрипты запрещают удалённую БД.

Для новой среды: `QA_FIXTURE_KIND=functional-audit node scripts/seed-ux-acceptance.cjs`. Fixture создаётся один раз и не перезаписывает существующий tenant.

Затем: `node scripts/test-access-http.cjs`. Проверяются anonymous 401, pending 403 и доступ к auth/me, expired billing 402 и управление аккаунтом, закрытый чат до/после удаления участника, scope balances/payroll/CSV export. Временные флаги и роли восстанавливаются; создаётся и удаляется только собственная тестовая группа.

HTTP-прогон требует запущенного API и seeded БД, поэтому пока не входит в обычный unit-test runner CI. Подключение полноценного изолированного HTTP-окружения CI и multi-tenant matrix остаётся в BASE-02–04.
